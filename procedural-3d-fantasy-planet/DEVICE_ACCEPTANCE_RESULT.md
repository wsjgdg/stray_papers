## 0. 一句话结论

这份 JSON 能证明「`pennants-81` 的 20 秒记录器在真实设备上完整跑完、报告自洽」，也能证明「这台机器在**最低档 SMOOTH** 上轨道 20 秒内仍有 **9.3%** 的回调错过一个 vsync（约 4.9 次/秒）」；它**不能**证明性能通过，因为文档要求的**地表**样本缺失、**手机**未覆盖，而且设备本身已经无档可降。

按文档「目标 60 FPS 是设计目标，不是这次已验证的承诺」的口径，本次判定维持**待验收**，不是「失败」——但也明确不是「通过」。

## 2. `1.148` 是怎么来的：这份数据全程在最低档

页面的像素比来自 `compact = pointer:coarse || innerWidth < 760`（`index.html:798`）。本次视口宽 **747 < 760**，所以这台台式机**走进了窄屏分支**：

```
基准比 = min(DPR 2, compact 上限 1.4, sqrt(1,900,000 / 563,238) = 1.837) = 1.4
SMOOTH 档 ×0.82 = 1.148        → 画布 857 × 865
```

三档是 `1.00 / 0.92 / 0.82`，SMOOTH 同时关掉第二层云、关叶卡、天气粒子降到 50%、轨道阴影步长放宽到 20 帧。也就是说：**这份记录里已经没有任何更省电的档位可切**。

为什么停在底档：本样本 EMA 平均帧时间 ≈ `0.906×16.7 + 0.093×33.5 ≈ 18.2 ms`。而策略要求 *EMA < 17.6 ms 持续 12 s* 才升档、*EMA > 22 ms 持续 3 s* 才降档（`index.html:9939` 的 `updateQuality()`，阈值在 9961–9962 行）。18.2 ms 恰在中间带，于是档位**粘在 SMOOTH**：既不会回升，也不会再降。这是策略的正常行为，但结论很实际——**这台设备在其允许的最低质量下仍然贴着预算跑**。

另需注意：一个 747 px 宽的桌面窗口拿到了移动端的 1.9 MP 预算，所以本次画布只有 741 k 像素。**分辨率并不高却仍然掉帧**，这一点在后面的归因里很关键。

## 3. 性能读数（ms，除注明外）

| 字段 | 含义 | n | 中位 | p95 | 最大 |
| --- | --- | --- | --- | --- | --- |
| `rafIntervalMs` | 上一次回调到本次回调 | 1097 | **16.7** | **33.3** | 49.9 |
| `cameraWallMs` | 相机更新 | 1098 | 0.1 | 0.2 | 0.4 |
| `worldWallMs` | 世界/剧情/动物推进 | 1098 | 2.9 | 6.2 | 10.7 |
| `patchWallMs` | 地表补丁刷新 | 1098 | 0 | 0 | 0.1 |
| `qualityWallMs` | 画质控制器 | 1098 | 0 | 0 | 0.1 |
| `renderCallWallMs` | **JS 侧 `renderScene()` 调用墙钟** | 1098 | **9.1** | 13.6 | 31.9 |
| `gpuMs` | GPU 查询（异步、限频 ≤10 次/秒） | **187** | **14.55** | **21.22** | 28.94 |
| 合计（上五项 CPU 阶段） | 同一次回调内相加 | 1098 | 12.2 | 18.1 | 34.5 |

**帧间隔分布**（60 Hz 下一帧 16.667 ms）

| 区间 | 帧数 | 占比 |
| --- | --- | --- |
| ≤ 17.5 ms（保住 60 Hz） | 994 | **90.6%** |
| 17.5 – 25 ms | 0 | 0% |
| 25 – 35 ms（**正好错过一个 vsync**） | 102 | **9.3%** |
| 35 – 60 ms | 1 | 0.1% |
| > 60 ms | 0 | 0% |

注意这个分布的形状：中间带是**空的**，所有慢帧都精确落在 `33.3–33.6 ms`。这不是「逐渐变慢」，而是一次次**单个 vsync 被错过**，频率稳定在约 `4.9 次/秒`。中位 16.7 ms 对应 59.9 回调/秒，而全程平均回调数只有 `54.8/秒`——两个数并不矛盾，差额就是那 9.3%。

**掉帧形态**：103 次掉帧分布在 97 段里，其中 **91 段只有 1 帧**、6 段 2 帧——几乎没有连续长卡顿。唯一的例外是**开头 1 秒掉了 9 帧**（该秒 50 个间隔里 18%），与面板收起和首帧着色器/纹理准备的时间窗吻合，属于启动成本，不是稳态。

**判读**：中位 `renderCallWallMs 9.1` + 世界 `2.9` ≈ 12.2 ms 的 CPU 阶段，配上 GPU 中位 `14.55 ms`，两条线都**贴在 16.667 ms 的预算上**，p95（18.1 / 21.2）都越过预算。所以掉帧更像是**临界预算的常态抖动**，而不是某个单点尖刺。

这里必须守住两条边界，否则数字会被读错：

- **不能把 CPU 阶段与 GPU 相加当作帧时间。** GPU 查询覆盖的是提交的 WebGL 工作，异步完成，不含完整合成/显示，本身还有采样开销（文档第 5 条、报告 `notes` 第 2–3 条）。所以只能说「两者各自接近或超过预算」，不能说「一帧共 26.7 ms」。
- **`renderCallWallMs` 不是 GPU 完成时间**，它是 JS 进 `renderScene()` 到返回的墙钟；驱动内部编译、队列阻塞都可能藏在里面，也可能完全在它之外。
- 只有 **187/1098 帧**有 GPU 样本（限频 ≤10 次/秒，与实现一致），所以任何「逐帧 GPU 归因」都缺少样本支撑。

**稳定性**：5 秒窗口的 GPU 中位依次为 `15.21 / 14.12 / 14.69 / 14.93 ms`，掉帧数 `39 / 19 / 22 / 23`。没有可见漂移，**但 20 秒太短**，不足以推断长时间运行、温度或省电模式下的表现——文档要求的「是否开启省电/低电量模式」本次也未记录。

## 4. 被这份数据排除的假设（负结果同样是结果）

我先怀疑过「周期性工作导致周期性掉帧」，因为时间线上看确实像一簇一簇。用帧号对齐检验后，这个怀疑**不成立**：

| 页面里的固定节奏 | 对齐比例（最高残类占比） | 随机基线 |
| --- | --- | --- |
| `frame % 20`（轨道 SMOOTH 阴影刷新步长） | 0.10 | 0.05 |
| `frame % 12`（叶卡高低模切换） | 0.11 | 0.08 |
| `frame % 2`（marker 更新） | 0.51 | 0.50 |

全部贴着随机基线，**没有明显高于 1/stride**，其中 mod 20 尤其接近基线。因此本记录**不支持**「周期性阴影刷新/叶卡切换是掉帧主因」这一猜测；它只说明掉帧是分散发生的。

同样可以排除（有直接证据，不是猜测）：

- `patchWallMs`、`qualityWallMs` 中位与 p95 都是 0 → 不是地表补丁刷新、也不是画质切换抖动；
- `transition` 全 `false` → 不是转场；
- `codexScanWallMs` 无样本 → 不是图鉴扫描。

**剩下的就是「渲染提交 + GPU 执行」这一段，而这份记录无法再往下分解**（驱动内部、GPU 队列、浏览器合成器都不可见）。文档也明确不宣称 `renderCallWallMs` 能代表 GPU 完成。

一个**推断**（有依据，但需要对照才能定论）：画布只有 741 k 像素、SMOOTH 档、bloom 已关，GPU 中位仍要 14.55 ms，而 `renderCallWallMs` 中位 9.1 ms 又与 294–300 次 draw calls 出现在同一帧里。这更像**提交/几何压力**（draw call 与 1.21 M 三角形的固定成本），而不是纯像素填充。验证办法见第 7 节，不需要改动生产画面。

## 6. 结论（严格表述）

**可以说**（都有 JSON 直接支撑）：

- `pennants-81` 在 Windows / Edge 156（Chromium 156）/ Intel Arc、视口 747×754、DPR 2、雪天、轨道、`SMOOTH` 档下完成 20 秒记录，1098 帧，采样 20 016.7 ms；
- 回调间隔中位 `16.7 ms`，**90.6%** 的间隔在 17.5 ms 以内，**9.3%** 为 `33.3–33.6 ms`（正好错过一个 vsync），最大 `49.9 ms`；
- CPU 阶段合计中位 `12.2 ms`、p95 `18.1 ms`；GPU 查询中位 `14.55 ms`、p95 `21.22 ms`（187 个样本）；
- 画质控制器在这台设备上已处于**最低档**且无档可降；
- 掉帧与页面的 mod 20 / mod 12 / mod 2 节奏**无对齐证据**。

**不可以说**：

- 「达到 60 FPS」「性能通过」「性能已优化」——中位回调 59.9/秒、平均 54.8/秒，且这是回调间隔而非呈现时间；
- 「地表流畅」「移动端可用」——地表与手机均无数据；
- 「图鉴/画面/声音/剧情通过」——全部未测；
- 「掉帧是阴影刷新造成的」——本数据明确不支持；
- 「驱动/合成器/GPU 队列是根因」——记录里没有这些可见性。

**关于「待验收」的说明**：本次不是验收失败。文档要求真人在真实设备上执行并通过/失败/未测记录，而这份数据只覆盖了其中「轨道性能采集」一条，且采集本身是成功的。因此状态保持**待验收**；同时它是一个**有用的负向信号**：底档 SMOOTH 在这台机器上仍每秒丢约 5 帧。

## 7. 建议的下一步（按信息量排序，都不需要改生产画面）

1. **补地表采集**（同设备、同档位、正常行走 20 秒）→ 这是文档明确要求的一项，也是唯一能和轨道对照的样本。地表阴影步长是 `3/5/8`（比轨道密），预计更重。
2. **同设备 `?aa=on` 与 `?aa=off` 各一次**（文档第 6 条允许的额外对照）→ 本页 `antialiasActual=true`，MSAA 的解析成本在 741 k 像素上是否显著，只有对照能回答。
3. **换两个窗口尺寸各采一次**（例如 900×600 与 1200×800）→ 这会改变 `compact` 分支（760 px 分界）与像素预算，可判断瓶颈随像素增长还是随画面内容不变。**这一步不需要改代码，却能区分填充率与提交/几何压力。**
4. **在带 GPU 的机器上跑 `npm run bench:render --prefix sims/browser`（设 `BROWSER_PERF_OUTPUT`）** → 与页面内记录交叉验证 `renderScene` 墙钟；注意无头模式可能落到软件渲染，必须核对输出里的 GPU 名称。
5. **真机（手机）竖屏与横屏各一次** → 移动端条目目前 0 覆盖；文档要求不能用模拟器代替。

若上面 3、4 指向提交/几何压力，下一步才是讨论批次与材质合并（历史记录里 24 区域分批在地表把 draw calls 从 124 增到 152，已判定为不可取）。**在拿到对照之前，不建议改任何渲染路径**；也不建议用「降低 SMOOTH 像素比」或「默认关 MSAA」这类改画面的手段换数字——文档明确不把隐藏/降质当作验收通过。
