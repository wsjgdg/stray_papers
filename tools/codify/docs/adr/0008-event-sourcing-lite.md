# ADR-0008: 事件日志是审计层叠加，不是完整事件溯源

状态：已接受（2026-09）

## 背景

用户要「撤销到昨天下午」和「查某个行动项从提出到完成的历史」。直觉方案是完整
事件溯源（当前状态由事件重放派生）。但那要重写存储层、用快照控制重放成本——
对一个单机个人工具，风险/收益严重不成比例，且重放 bug 会直接损坏唯一数据源。

## 决策

`src/lib/eventJournal.ts`，event-sourcing-**lite**：

- **主状态仍是会议对象本身**（存 IDB meta），事件日志是叠加其上的**变更审计层**——
  当前状态不由事件重放派生；
- 每个事件记字段级 `prev/next` 差异；**回滚 = 对目标时刻之后的事件逆序应用 prev**
  （`buildRevertPatch`）；
- **大文本字段（单值 > 6000 字符，`VALUE_CAP`）只记长度不记内容**——转写稿全文
  进日志会让体积失控；这类事件标记为不可回滚，UI 如实禁用并说明；
- **不支持部分回滚**：目标时刻之后只要有一个事件不可回滚（大文本/截断差异/信息型），
  `buildRevertPatch` 返回 null——半新半旧的拼接状态比不回滚更糟；
- 有 id 的列表字段（actions/decisions/pendingActions/notes）做**条目级差异**，
  支撑「某个行动项的履历」与条目级回滚；
- **写入尽力而为**：日志写失败绝不阻塞业务写入（catch 吞掉）；
- 容量滚动淘汰：每场会议 ≤ 80 条（`PER_MEETING_CAP`）、全局 ≤ 2000 条（`GLOBAL_CAP`）；
- 同会议同字段集的连续标量变更（转写击键）在 60s 窗口内合并（`COALESCE_MS`），
  避免一次会议录音产生上千条击键事件；
- 不随备份导出（备份契约不变）。

## 考虑过的替代方案

- 完整事件溯源：见背景，重写存储层 + 快照 + 重放，单机工具不值当，且重放 bug
  直接威胁唯一数据源；
- 只存「当前状态 + 单个撤销栈」：刷新即丢，无法「撤销到昨天」，无法查条目履历；
- 大文本也记全文差异：体积失控（一场会议改十次转写稿 = 十份全文），且 90% 的
  转写稿变更不需要回滚——只记长度是诚实的取舍；
- 部分回滚（跳过不可回滚事件）：产生半新半旧的拼接状态，用户无法预期，宁可整体拒绝。

## 何时重新评估

- 引入多设备同步（届时事件日志天然适合同步原语，可能升级为真正的溯源）；
- 用户反馈「大文本也想回滚」强烈——可考虑对转写稿单独做分片级快照而非全文差异；
- 单用户会议数常态超千场，全局 2000 条上限需要重新标定（当前每场 80 条 × 千场
  远超全局上限，淘汰会先于单场上限触发）。
