# ADR-0003: RAG 重排用 RRF 名次融合，不用神经交叉编码器

状态：已接受（2026-09）

## 背景

问答要在几十上百场会议里选出「真正相关」的少数几场进 LLM 上下文。旧版全库直塞
80k 字符：大档案下 token 爆炸，且噪音会议稀释注意力、拉低忠实度。需要召回 + 重排。
两路召回信号（向量余弦、词面 bigram 命中率）**量纲不可比**——余弦 0.6 和命中率 0.4
谁更相关没有意义。

## 决策

`src/lib/ragPipeline.ts`，三段式「召回 → 重排 → 生成」：

- **召回（宽口径宁漏勿缺）**：向量通道取 Top-50 段（`VECTOR_RECALL_TOP`，语义索引
  就绪时）；词面通道对头部字段粗排后扫前 20 场（`LEXICAL_MEETING_SCAN`）做块级
  bigram/词元密度打分。语义索引未启用时词面是唯一通道，管线不断供；
- **重排用 RRF**（Reciprocal Rank Fusion，`RRF_K=60`）：只用两路的**名次**不用原始分，
  `score = Σ 1/(k + rank)`——天然免疫量纲问题；k=60 是 RRF 原论文经验值，压头部过度主导；
- **进上下文**：重排后 Top-5 场（`RERANK_MEETINGS`），每场 ≤2 个最相关转写片段
  （`CHUNKS_PER_MEETING`）、片段预算 1600 字符（`CHUNK_CONTEXT_CAP`）；
- **小档案直塞**：≤5 场（`SMALL_ARCHIVE`）跳过检索全库进上下文——本来就装得下，
  检索反而可能漏；
- `rerankChunks` 是独立纯函数：将来换交叉编码器 / LLM 精排只改这一个函数，管线其余不动。

## 考虑过的替代方案

- 神经交叉编码器（cross-encoder）：精度更高，但浏览器内要再引入数十 MB 模型资产，
  且每对 query×doc 一次前向——与「零费用、离线可用」的产品立场冲突，否；
- 加权线性融合两路原始分：需要先归一化 + 调权重，量纲问题只是被掩盖没被解决；
- LLM 直接精排全部召回结果：每次问答多一轮 LLM 调用，延迟与费用翻倍；
- 只做向量召回不做词面：专有名词/编号/人名这类精确匹配向量召回经常漏，词面兜底必要。

## 何时重新评估

- 评估台（EvalBench）显示「相关会议没被选进上下文」成为答错主因（重排召回不足）；
- 本地小体积交叉编码器成熟（如 < 20MB 的量化 reranker），可在可接受资产下换 `rerankChunks`；
- 单用户会议数常态超过数几百场，Top-50 召回口径需要重新标定。
