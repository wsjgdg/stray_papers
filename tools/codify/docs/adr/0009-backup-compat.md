# ADR-0009: 备份兼容双轨制——迁移注册表为主通道，宽容解析只做兜底

状态：已接受（2026-09）

## 背景

两年后 schema 到 v5，v1 的备份还要能导入。早期策略是「只允许新增可选字段 +
宽容解析兜一切」——不写迁移脚本。这在字段只增不改时成立，但一旦出现字段改名、
删除、语义变化（v2 的「行动项」在 v5 里换了结构），宽容解析就会**静默丢数据**：
读不认识的字段当缺失、回退默认值，用户导入后才发现历史行动项没了。把结构演进
全压给宽容解析，正是用户点名的「万能解析器技术债」。

## 决策

双轨制，`src/lib/schemaMigrations.ts`（主通道）+ `src/lib/store.ts`（兜底）：

- **迁移注册表**：`MIGRATIONS[N]` = vN→vN+1 的纯函数。导入时 `applyMigrationChain`
  从备份自带 version 起**链式调用**到当前版（`SCHEMA_VERSION`）。禁止跳版——
  注册表出现空洞，链在断点如实停下（`stoppedAt` 标记 + console.error），
  剩余差异才交给宽容解析；
- **单步迁移不抛异常**：某步 throw 被链执行器捕获、记日志、停在当前版——
  一次坏迁移不毁掉整份备份的导入；
- **宽容解析降为最后防线**（`validateBackupObject`）：只兜「新增可选字段」这类
  天然兼容差异 + 迁移后的残留噪音（缺失回退默认、多余忽略、非法丢弃）。
  它不再是结构演进的主通道；
- **版本闸门**：备份声明的 `minReaderVersion` 高于本工具 `APP_VERSION` → 明确拒绝
  （「请升级后再导入」），不带病解析；version 更高（未来导出）不迁移、宽容尝试读取；
- `BACKUP_VERSION` / `APP_VERSION` 都引用 `SCHEMA_VERSION`——「导出版本」「迁移链终点」
  「可读上限」永远是同一个数，不会漂；
- **新增一版的操作清单**（写进 schemaMigrations.ts 头注释）：写迁移函数 → 注册 →
  SCHEMA_VERSION+1 → golden set 加「vN 样本→迁移→断言」用例 → 真实旧备份样本进 fixtures。

## 考虑过的替代方案

- 纯宽容解析（旧策略）：结构变更时静默丢数据，用户导入后才发现——正是技术债，否；
- 纯迁移脚本不留宽容解析：未来版本导出的备份（version 更高）无法宽容读取，
  且迁移后仍可能有未知字段需要安全忽略——宽容解析作为兜底有其价值；
- 一个大 `parseAnyVersion` 万能函数：所有版本逻辑搅在一起，每加一版都在同一坨里
  改，无法单独测试某一版的迁移——注册表把它拆成一版一函数；
- 允许跳版迁移（v1 直接到 v5）：组合爆炸且难测试，链式一版一步可组合可单测。

## 何时重新评估

- 第一次真正的结构变更（v1→v2）落地时，验证链式迁移 + golden set 用例的流程是否顺手；
- 备份格式需要支持增量/差异导出（当前是全量快照），迁移语义要相应扩展；
- 引入云同步后，多设备版本不一致成为常态，迁移链要处理「降级读取」（高版本数据
  在低版本工具里安全只读）。
