# ADR-0005: Prompt 三铁律——合法 JSON / 禁止编造 / 低置信交人工 + 逐字引用

状态：已接受（2026-09）

## 背景

会议纪要工具的 LLM 产出直接进用户档案：编造一条不存在的行动项、虚构一个决定，
比「漏抽一条」危害大得多——用户会拿着错信息去执行。同时下游要机器解析这些产出
（渲染成卡片、进检索索引），格式漂移会让整条链断掉。

## 决策

所有抽取/生成类 prompt（`src/lib/ai.ts`）贯彻三条铁律，措辞可微调、原则不可破：

1. **输出必须是合法 JSON，不要输出 JSON 以外的任何文字**——下游 `JSON.parse` 直接消费，
   不容许 markdown 围栏/前后缀解释（整理器类例外：产出是纯文本全文，铁律改为
   「直接输出整理后全文，不要解释/前言/代码围栏」）；
2. **只依据给定原文，禁止编造**——每条抽取类 prompt 都显式写「禁止编造原文中不存在的
   信息」「资料里没有就直说找不到」；摘要器进一步要求「每个要点只能来自其议题引用的
   事实，禁止引入清单外信息」；
3. **低置信交人工，不硬凑**——「把握不足如实给低 confidence，交人工复核，不要为了
   凑数硬给高分」；审查器「合格就返回空 issues，不要为了凑数硬挑刺」；
   引用审查器「宁可判 weak 不要虚给 strong」。

配套**逐字引用**（source_quote）：抽取的每条事实/行动项必须附「从原文逐字摘录的支撑句」，
`verifyCitations` 再把答案引文与原文归一化对账（去空白标点、大小写无关）算 verbatim
命中率——「引用在原文里存在」由机器核验，不靠人眼扫。

## 考虑过的替代方案

- 自由文本输出 + 正则解析：格式漂移即断链，且无法机器核验，否；
- function calling / JSON schema 强约束：平台网关不保证所有模型都支持 tool_call，
  退化成文本时仍要兜底解析——prompt 铁律 + 宽容 JSON 提取是最大公约数；
- 只做「禁止编造」不做逐字引用：没有机器可核验的锚点，忠实度全靠模型自觉，无法量化；
- 高置信阈值一刀切：不同任务（抽取 vs 标注）容错成本不同，阈值分角色设定（见 ADR-0006）。

## 何时重新评估

- 平台网关稳定支持结构化输出（JSON mode / tool_call），可把铁律 1 从 prompt 约束
  升级为协议约束；
- 评估台显示某类 prompt 的编造率 / 格式失败率长期为 0，可考虑放宽对应措辞（减 token）；
- 引入新模型代际，需用评估台 golden set 重测三铁律的实际遵守率。
